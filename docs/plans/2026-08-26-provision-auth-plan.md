# План: парольная аутентификация провижна (issue #31, волна 1)

Дата: 2026-08-26. Цель волны — сделать провижн пригодным к работе как **общая
инсталляция** для нескольких админов. Вторая волна (Docker/compose/CI/доки) —
отдельным issue.

Решения maintainer'а: один общий пароль без учётных записей; первичный из env,
далее меняется в UI; TLS терминирует обратный прокси; образ в GitLab registry.

## Архитектурная проверка

1. **Документы:** `docs/threat-model.md` (обязательно — меняется trust zone),
   README (раздел про веб), `docs/notifications.md` не затронут.
2. **Инварианты:** протокол, токен, инвайты, рендер `.rsc` — не затрагиваются
   вообще. Меняется только фронтенд провижна и его транспортная обвязка.
3. **Совместимость:** локальный режим (`serve` на loopback, Wails-десктоп)
   работает как раньше и без пароля — иначе сломаем текущий сценарий владельца.
   Формат `mkpk.yaml` не меняется.
4. **Новые файлы:** `client/internal/web/auth.go` (+тесты); файл учётных данных
   `mkpk-admin.json` рядом с конфигом — **отдельно от `mkpk.yaml`**, потому что
   конфиг копируют, диффают и передают, а материал аутентификации там не нужен.
5. **Зависимости:** новых нет. `golang.org/x/crypto` уже в модуле (ssh) —
   берём оттуда `argon2`.
6. **Локализация:** экран логина и смена пароля — EN/RU через существующий `t()`.
7. **Живой роутер:** не нужен.

## Дизайн

**Режимы.** Аутентификация включается, когда рядом с конфигом есть файл учётных
данных либо задан `MKPK_ADMIN_PASSWORD`. Без этого поведение прежнее: loopback +
per-session токен. Бинд на не-loopback адрес разрешается **только** при
включённой аутентификации и явном `--behind-proxy`; иначе — отказ на старте с
понятным сообщением.

**Хранение пароля.** `mkpk-admin.json` (0600, атомарная запись):
`{"v":1,"algo":"argon2id","salt":…,"hash":…,"params":{…},"updated_at":…}`.
Пароль в открытом виде не хранится нигде. `MKPK_ADMIN_PASSWORD` используется
только для первичной установки (если файла нет); при существующем файле env
игнорируется, о чём пишется в лог. CLI: `mkpk-provision passwd [--config …]`.

**Сессии.** Серверные, в памяти (перезапуск = разлогин, это приемлемо и
безопаснее персистентных): `id` = 32 случайных байта, cookie `mkpk_session`
(HttpOnly, SameSite=Strict, Path=/, Secure при TLS или `--behind-proxy`),
скользящее продление, абсолютный предел. Смена пароля инвалидирует все сессии,
кроме текущей.

**CSRF.** Существующий заголовок `X-MKPK-Token` сохраняется и становится
per-session: значение генерируется вместе с сессией и вшивается в страницу.
Кастомный заголовок нельзя отправить кросс-сайтом без CORS-preflight, плюс
SameSite=Strict — этого достаточно, отдельного механизма не заводим.

**Троттлинг.** Счётчик неудач на IP и глобальный; после N неудач — задержка,
растущая экспоненциально, с потолком. Успешный вход сбрасывает счётчик.

**Потеря правок при одновременном редактировании.** `/api/config` отдаёт
`version` (sha256 файла); мутирующие вызовы шлют его обратно заголовком
`X-MKPK-Config-Version`. Несовпадение → `409` и просьба перезагрузить.
Это единственная защита, которая нужна: в общей инсталляции конфиг один.

## Заметка для волны 2 (Docker)

Решение maintainer'а: поставляем **два варианта compose**, а не один.

1. **Out-of-box** — Caddy рядом в compose, автоматические сертификаты Let's Encrypt,
   для случая «есть домен, хочу поднять и забыть».
2. **За готовым ингрессом** — только контейнер провижна на внутреннем адресе,
   TLS и маршрут (`https://somedomain` → `mkpk_provision:port`) уже обеспечены
   существующей инфраструктурой. В этом варианте Caddy в поставку не входит.
