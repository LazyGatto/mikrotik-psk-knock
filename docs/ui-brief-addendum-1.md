# Апдейт брифа №1 — юзеры на верхнем уровне, мультироутерный доступ

**Статус:** дополнение к [ui-brief.md](ui-brief.md). Исходный бриф уже в работе —
этот документ описывает **дельту** поверх него, не заменяя целиком. Применять
вместе: всё из ui-brief.md остаётся в силе, кроме явно переопределённого ниже.

## Суть изменения (одним абзацем)

Раньше юзер принадлежал одному роутеру (лежал внутри него). Теперь **юзер —
сущность верхнего уровня, рядом с роутерами**, и может иметь доступ к **нескольким
роутерам** сразу. Один человек — одна личность в приложении; ему выдаётся один
инвайт, в котором может быть **несколько роутеров** с разными портами и сервисами.
Клиентское приложение импортирует один блоб и показывает список роутеров.

## Новая модель данных

- Верхний уровень конфига теперь двухсоставной: **Роутеры** и **Юзеры** (две
  топ-левел сущности вместо «юзеры внутри роутера»).
- **Матрица доступа** становится трёхмерной: `юзер → роутер → [сервисы]`. Юзер
  выбирает, к каким роутерам и к каким их сервисам он допущен.
- **`client_id` — один общий на юзера** (единая идентичность во всех роутерах/
  блобах). Это просто идентификатор в формуле токена.
- **PSK — свой на каждую пару (юзер × роутер)**, НЕ один общий на юзера. Это не
  вопрос вкуса, а требование изоляции (см. ниже). В UI это скрытая механика:
  оператор видит одного юзера, PSK генерятся/ротуются per-router под капотом.

### Почему PSK per-роутер (для дизайна — просто принять как факт)

Отрендеренный конфиг роутера **содержит сырой PSK** юзера (он нужен роутеру, чтобы
сверять токен). Значит, компрометация конфига одного роутера не должна давать
доступ к другим. Поэтому у каждого (юзер, роутер) — свой секрет. На UI это влияет
только тем, что «ротация PSK» и «отзыв» может быть per-router, а не глобально на
юзера (в мокапах достаточно предусмотреть, что у доступа к каждому роутеру свой
жизненный цикл).

## Инвайт-блоб — мультироутерный

- Блоб теперь несёт **список роутеров**: для каждого — адрес, `bucket_seconds`,
  его сервисы (порты + порт для TCP-check) и **его PSK**. `client_id` — один на
  весь блоб.
- **Два режима экспорта** (оператор выбирает при выдаче):
  1. **Все роутеры юзера — одним блобом** (удобно, дефолт для доверенного юзера).
  2. **Только выбранный роутер** — для чувствительных случаев, чтобы не класть в
     один блоб доступ ко всему.
- Радиус поражения: бандл нескольких роутеров в один блоб осознанно расширяет
  «цену компрометации блоба» до всех роутеров внутри. Это ок как дефолт, но именно
  поэтому нужен режим «только один роутер». В модалке выдачи это стоит показать
  явно (что войдёт в блоб) + сохранить предупреждение про safe-env.

## Что меняется в навигации и экранах

- **«Юзеры» становятся верхним разделом**, рядом с «Роутерами» (а не вложенной
  секцией внутри роутера). Это ключевое изменение верхней навигации относительно
  исходного брифа.
- **Экран юзера** = его идентичность (имя, `client_id`) + **матрица доступа**:
  список роутеров, под каждым — чекбоксы его сервисов. Здесь же кнопка «invite» с
  выбором режима экспорта (все / выбранный роутер).
- **Экран роутера** больше не «владеет» юзерами: вместо таблицы юзеров — read-only
  список «кто имеет доступ к этому роутеру и к каким сервисам» (навигация к юзеру).
  Сервисы, креды деплоя, render, deploy у роутера — без изменений.
- **Модалка invite** — мультироутерная: показывает, какие роутеры/сервисы войдут
  в блоб, и переключатель режима экспорта.

## Что НЕ меняется

- Терминология (роутер / сервис / юзер / токен-как-производное), инварианты
  безопасности, креды деплоя на уровне роутера, тоггл сервиса, индикатор
  незадеплоенных изменений, экран Render, экран Deploy — всё как в ui-brief.md.
- Свобода дизайнера — та же: разбивка/экраны здесь описывают **требования**, а не
  жёсткий визуал; предлагай лучше, опираясь на UI/UX best-practices. Жёстко
  зафиксированы только продуктовая модель/термины и безопасность.

## Порты стука: ручной ввод или рандом + проверка коллизий

Три «стучальных» порта сервиса (stage1 / stage2 / token) можно:
- **ввести вручную**, либо
- **подставить рандомом по кнопке** («сгенерировать свободные порты»).

Требование: порты не должны пересекаться с уже занятыми **в пределах роутера** —
ни с другими сервисами (их stage1/stage2/token), ни с портами цели сервиса.
Проверка нужна на **бэкенде (авторитетно, отклоняем коллизию с внятной ошибкой)** и
дублируется на фронте для мгновенной подсказки. Кнопка рандома подбирает заведомо
свободные значения (бэкенд может отдавать набор свободных портов). Сейчас такой
кросс-сервисной проверки нет — это доработка и модели, и UI.

## Пересмотр NAT: у сервиса — явный «тип цели», а не тоггл NAT

**Проблема текущей модели.** Смысл стука — пропустить клиента к цели: knock кладёт
его IP в address-list, а цель этот список потребляет. Сейчас **единственный
потребитель списка — одно dst-nat правило**. Поэтому:
- сервис с выключенным NAT не делает ничего (список наполняется, но никто не
  читает) — мёртвое состояние;
- цель (`to_address:to_port`) требуется указывать всегда, даже когда NAT выключен —
  то есть заставляем задавать бессмысленное поле;
- кейс «просто порт на самом роутере» вообще не поддержан — умеем только проброс
  внутрь сети.

**Решение.** Убрать тоггл «NAT вкл/выкл». У сервиса — обязательный **тип цели**:

- **forward (dst-nat)** — проброс на внутренний хост. Поля: внешний порт на
  роутере, `to_address`, `to_port`, протокол (tcp/udp). Генерит dst-nat, гейтованный
  allowed-list сервиса.
- **local (input)** — доступ к порту **самого роутера** (его SSH/WireGuard/API/…).
  Поля: порт на роутере, протокол. Генерит `input accept`, гейтованный allowed-list.
  NAT нет.

Следствия:
- у каждого сервиса всегда есть осмысленная цель (это и есть суть сервиса —
  гейтованный эндпоинт); «пустого NAT» не существует;
- `enable/disable` сервиса = включить/выключить его правила на роутере (как и
  задумано), без отдельного второго тоггла у NAT;
- в UI форма сервиса показывает поля по выбранному типу (переключатель
  forward/local), а не всегда-видимый блок NAT;
- порт для клиентского TCP-check в блобе = внешний порт сервиса в обоих типах
  (проброс — внешний dst-port; local — порт роутера), клиентская проверка не
  усложняется.

Это меняет и модель (тип цели вместо `nat.enabled` + всегда-обязательная цель), и
рендер (для `local` — правило `input accept` вместо/помимо dst-nat). Backend-задача
отдельная; здесь фиксируем целевое поведение для мокапов.

## Открытый момент для проработки в мокапах

Как удобнее строить матрицу доступа при большом числе роутеров/сервисов: со стороны
юзера (юзер → чекбоксы роутеров и сервисов) или со стороны роутера (на роутере —
кого пускаем), либо обе проекции одной матрицы. Предложи вариант.
