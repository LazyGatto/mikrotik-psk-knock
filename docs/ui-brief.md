# Бриф на мокапы админского UI (mkpk-provision)

Задача для дизайн/UI-агента: подготовить мокапы веб-UI провижининг-приложения.
Backend и API уже работают (см. `internal/web`, `internal/admin`); нужен
продуманный UX и визуал, потом возьмём готовые мокапы в разработку. Это НЕ задача
на код — только мокапы + описание взаимодействий.

## Что это за приложение

`mkpk-provision serve` — локальное веб-приложение (крутится на `127.0.0.1`, только
loopback, с per-session токеном), которым **администратор** настраивает
порт-knock защиту на своих MikroTik-роутерах и раздаёт доступ конечным юзерам.
Это внутренний операторский инструмент (не публичный SaaS): один пользователь —
сам админ — за своей машиной. Дальше планируется упаковка в десктоп-приложение
(Wails), так что дизайн должен работать как полноценное настольное приложение, а
не как лендинг.

Полная продуктовая модель — в [admin-app.md](admin-app.md). Ниже — выжимка для
дизайна.

## Сущности и терминология (соблюдать в UI)

- **Роутер** — MikroTik, который провижиним по SSH. Верхний уровень навигации:
  один конфиг содержит **много роутеров**, всё остальное принадлежит выбранному
  роутеру.
- **Сервис** — гейтируемый порт-форвард: три «стучальных» порта (stage1 / stage2 /
  token) + NAT на внутренний `host:port`. Пример: `ssh-home`, `web-home`. У
  сервиса есть флаг **вкл/выкл** (на уровне конфига), опциональный NAT и
  опциональные уведомления (webhook / telegram / email).
- **Юзер** — личность с одним PSK, которой разрешён **набор сервисов** (матрица
  доступа юзер×сервис). В коде исторически называется `client`; в UI показываем
  как «user».
- **Токен** — НЕ объект настройки, не показываем как редактируемую сущность. Это
  эфемерное значение, которое клиентское приложение само пересчитывает. В UI
  токенов нет.
- **Invite-blob** — компактная строка (base64url), персональный «слепок доступа»
  одного юзера (адрес роутера, его PSK, разрешённые ему сервисы с портами).
  Админ генерит его на юзера и передаёт **только в безопасном канале**.

Иерархия: `Роутер → (Сервисы, Юзеры)`. Юзер ссылается на сервисы того же роутера.

## Ключевые пользовательские флоу

Мокапы должны покрыть эти сценарии:

1. **Первый запуск / пустой конфиг** — ещё нет роутеров. Онбординг: «добавьте
   первый роутер» (имя + адрес).
2. **Добавить/выбрать роутер** — селектор роутера вверху; добавление (имя, адрес),
   удаление (с подтверждением, т.к. уносит его сервисы и юзеров).
3. **Настроить сервис** — добавить сервис (имя, три порта, опц. NAT, опц. notify);
   **отредактировать существующий** (сейчас нельзя — это боль, см. ниже);
   включить/выключить; удалить.
4. **Завести юзера** — имя, чекбоксы «каким сервисам этого роутера открыт доступ»,
   PSK (сгенерировать или ввести). Редактирование набора сервисов юзера, удаление.
5. **Выдать доступ** — на юзере кнопка «invite» → показать blob → скопировать /
   скачать `.mkpk`. Обязательно предупреждение «передавать только в safe-env,
   содержит PSK».
6. **Рендер конфига** — показать сгенерированный `.rsc`, скачать его.
7. **Деплой по SSH** — форма подключения (адрес/порт/user/ключ/пароль/agent) и три
   действия: **Status** (что установлено, есть ли расхождение), **Apply**
   (залить), **Uninstall** (снести). Есть режимы `dry-run` и `force`. Нужен
   вывод результата (лог/JSON).

## Текущая реализация (отправная точка)

Сейчас всё на одной длинной странице (см. `internal/web/assets/index.html`):
шапка → бар роутера → секции Services, Users → грид Render + Deploy → модалка
Invite. Работает функционально, но UX сырой. Скриншот-состояние можно получить,
запустив `mkpk-provision serve` локально.

**Что просим переосмыслить (punch-list из живого тестирования 2026-07-27):**

- **Разделы вместо одного полотна.** Логичнее разнести на навигацию: Роутеры /
  Сервисы / Юзеры / Render / Deploy (табы или боковое меню). Контекст «текущий
  роутер» — сквозной.
- **Тоггл вкл/выкл сервиса неочевиден.** Сейчас это голый чекбокс без подписи.
  Надо явно показать: он правит состояние сервиса **в конфиге** (эффект
  применяется только после Deploy), а НЕ переключает что-то мгновенно на роутере.
  Нужны понятные лейбл/состояние/подсказка.
- **Нельзя редактировать существующий сервис** — только добавить/удалить. Нужна
  форма редактирования (порты, NAT, notify).
- **Нет индикатора «есть незадеплоенные изменения».** Бэкенд уже считает
  per-router hash и умеет сравнивать с тем, что реально стоит на роутере (drift).
  Нужен явный статус: «локальный конфиг ≠ то, что на роутере → нужен Deploy».
  Показывать на уровне роутера и, возможно, помечать изменённые сервисы/юзеров.
- **Форма деплоя.** По умолчанию включён `use ssh-agent`, из-за чего первый Status
  часто отдаёт ошибку — нужно продумать дефолты и внятную обработку/отображение
  ошибок подключения. Разделить «параметры подключения» и «действия».
- **Render** может быть длинным — нужен аккуратный скролл/перенос, не ломающий
  верстку (была проблема с горизонтальным скроллом на всю страницу).
- **Опасные действия** (удалить роутер, Uninstall) — явные подтверждения и
  визуальное выделение.

## Ограничения и тон

- Локальное операторское приложение, не публичный сайт. Плотный, «приборный»
  интерфейс уместнее маркетингового. Целевой контекст — десктоп (Wails), но верстка
  адаптивная.
- **Секреты.** PSK и SMTP-пароли не покидают машину админа. В UI PSK/пароли —
  через `password`-поля; invite-blob всегда со шторкой-предупреждением про safe-env.
- Язык интерфейса — как в текущей версии (микс, заголовки/термины можно
  причесать). Уточнить у заказчика, делаем ли полноценную локализацию.
- Технически всё останется на vanilla (embed-ассеты, без внешних CDN — строгий
  CSP в проде). Мокапы могут это не учитывать, но тяжёлых фреймворк-компонентов
  лучше избегать концептуально.

## Что нужно на выходе

- Мокапы ключевых экранов: пустой стейт, роутер с сервисами и юзерами, форма
  добавления/редактирования сервиса, форма юзера с матрицей сервисов, модалка
  invite, экран Render, экран Deploy (включая состояние ошибки и состояние
  «drift/нужен деплой»).
- Схема навигации между разделами и где живёт «текущий роутер».
- Описание состояний тоггла сервиса и индикатора незадеплоенных изменений.
- Опционально: лёгкий визуальный язык (типографика, цвета статусов on/off/drift/
  ошибка).

Вопросы к заказчику до старта: (1) нужна ли полноценная локализация; (2)
предпочтение по навигации — верхние табы vs боковое меню; (3) насколько
«десктопным» должен ощущаться интерфейс уже сейчас.
