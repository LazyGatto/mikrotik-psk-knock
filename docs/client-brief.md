# Бриф: клиентское приложение mkpk (macOS menu-bar)

Документ для проработки мокапов клиентского приложения — того, чем пользуется **получатель
инвайта** (не оператор). Оператор раздаёт `.mkpk`-файл; пользователь импортирует его и в пару
кликов «стучится», чтобы временно открыть себе доступ к сервису на роутере.

## 1. Роль и контекст

- Делает то же, что CLI `mkpk knock` / `mkpk check`, но в фоне и в GUI.
- Крипто-рантайм — client-side (staged UDP + PSK-time-token). Приложение ничего не знает про SSH,
  провижининг и внутренности роутера — только адрес, порты и PSK из инвайта.
- Цель — «нажал → открылось». Пользователь может быть нетехническим.

## 2. Форм-фактор

- **macOS, menu-bar приложение** (NSStatusItem), фоновый процесс, без основного окна и без иконки в доке.
- Клик по иконке в баре → **попап** (панель ~360–420pt шириной, авто-высота под контент), закрывается
  по клику снаружи / Esc.
- Всё живёт в попапе: список сервисов, статусы, действия, настройки.

## 3. Иконка в menu-bar (состояния)

Иконка отражает общее состояние, чтобы проблему было видно, не открывая попап:

- **Покой** — нейтральная иконка (нет открытых сервисов, всё ок).
- **Есть открытое** — акцент (напр. зелёная точка/заливка), опц. пока хотя бы один сервис открыт.
- **Внимание** — янтарный акцент: последний стук не открыл порт, роутер недоступен, или проблема с
  часами роутера (стук не будет работать).

Открытые для дизайна варианты: только-иконка vs иконка+короткий текст/бейдж рядом (macOS позволяет
текст у status item). Предпочтение — не перегружать: скорее цветовое состояние иконки, чем счётчики.

## 4. Попап — структура

**A. Пустое состояние (нет инвайтов).** Приглашение импортировать: кнопка «Открыть .mkpk», зона
drag-n-drop, «вставить блоб». Короткое объяснение, что такое инвайт и откуда его взять.

**B. Основной экран.** Сгруппировано по роутеру:
- Заголовок попапа: `client_id`, кнопка импорта (+), шестерёнка настроек.
- Секция роутера: адрес роутера, индикатор доступности/часов.
- Карточки сервисов (см. §5).
- Возможно действие уровня роутера: «Стукнуть всё».

**C. Настройки** (отдельный экран/лист попапа): см. §9.

## 5. Карточка сервиса — состояния

Данные на карточке: имя сервиса, `адрес:check_port`, индикатор статуса, действия.

Состояния индикатора:
- **unknown** — ещё не проверяли (или `check_port = 0` → авто-проверка недоступна).
- **checking** — идёт TCP-проверка (спиннер).
- **open** — порт открыт (TCP-connect прошёл).
- **closed** — порт закрыт (refused/timeout).
- **knocking** — идёт стук (несколько секунд: стадии + токен + ожидание bucket).
- **error** — ошибка (нет сети, не резолвится адрес и т.п.).

Действия: **«Стук»** (стук → авто-проверка) и **«Проверить»** (только check). Опц. показывать время
последнего успешного стука / «открыто ещё ~N мин» — но точный TTL клиент не знает (он на роутере),
так что либо без обратного отсчёта, либо приблизительно.

## 6. Взаимодействия

- **Стук:** нажатие → `knocking` (спиннер) → авто-`check` с несколькими ретраями → `open`/`closed`.
- **Проверить:** `checking` → `open`/`closed`.
- **Импорт/реимпорт:** открыть файл, drag-n-drop, вставить блоб. Реимпорт того же клиента/роутера
  **обновляет** существующую запись (например, оператор перевыпустил PSK).
- **Удалить инвайт/роутер** из списка.

## 7. Данные из инвайта (что реально есть)

На роутер: адрес, `bucket_seconds`, `psk` (секрет). На сервис: `name`, порты `stage1/stage2/token`,
`check_port`. Протокол таргета, внутренний бэкенд и TTL доступа в блоб **не входят** — значит статус
только open/closed по TCP к `check_port` (если он `0` — только стук, без авто-проверки).

## 8. Обратная связь и диагностика

После неудачного стука показываем **человеческую** подсказку (у CLI уже есть точная диагностика):
- порт **refused** → «дошло до роутера, но за сервисом никто не слушает / не тот порт»;
- порт **timeout** → «стук не открыл — возможно, часы роутера разошлись или сеть режет UDP».

Ошибки — явные и дружелюбные, без «тихих» провалов.

## 9. Настройки

- **iCloud-синк инвайтов** (тумблер, по умолчанию — обсудить). Синхронизация импортированных инвайтов
  между маками пользователя под одним Apple ID. Секреты (PSK) — только через **iCloud Keychain** /
  шифрование, не через обычный iCloud KV.
- **Автозапуск при логине** (тумблер).
- **Уведомления** macOS на успех/провал стука (тумблер).
- Опц.: глобальный хоткей на «стук» избранного сервиса (как KeyboardShortcuts у OpenUsage).
- О приложении / версия / авто-апдейты (Sparkle).

## 10. Визуальное направление

- Нативный macOS-вид (SwiftUI), поддержка светлой/тёмной темы, соответствие современному языку
  (возможно Liquid Glass для панели). Не веб-верстка — настоящая маковая панель.
- Желательно перекликаться по «характеру» с провижн-UI (та же семья иконок/акцентов), но это
  отдельное приложение со своим, более компактным ритмом.
- Иконка приложения — на базе существующей `mkpk-icon` (стук + щит), возможно упрощённый монохромный
  вариант для menu-bar (template image, чтобы корректно работал в светлой/тёмной панели).

## 11. Зафиксированные технические решения (контекст для дизайна)

- Стек: **нативный Swift 6 / SwiftUI**, SPM; UI в AppKit-owned `NSStatusItem` + кастомный `NSPanel`.
- Рантайм стука/проверки **реализован на Swift** (CryptoKit SHA-512 токен, Network.framework UDP/TCP),
  с golden-тест-векторами против Go-эталона, чтобы формула токена не разъехалась.
- Живёт в этом же репозитории (`client-macos/`); провижининг остаётся Go/Wails.
- Дистрибуция: подписанный+нотаризованный DMG, авто-апдейты Sparkle.

## 12. Открытые вопросы для дизайна

1. Иконка в баре: только состояние-цвет, или ещё текст/бейдж рядом?
2. iCloud-синк по умолчанию включён или выключен?
3. Нужен ли экран «детали сервиса» (лог последних стуков, диагностика), или всё в карточке?
4. «Стукнуть всё» на роутер — нужно ли, и как показывать агрегированный результат?
5. Онбординг первого запуска — насколько подробный (объяснять концепцию стука)?
