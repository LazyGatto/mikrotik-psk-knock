# Админ-приложение и раздача клиентам

Согласованная продуктовая модель провижининг-приложения (`mkpk-provision`: CLI +
локальный веб-UI, далее Wails-десктоп) и способа доставки конфигурации конечному
юзеру. Опорный документ для соответствующего этапа работ (см. roadmap).

## Сущности

- **Роутер** — MikroTik, который мы провижиним по SSH.
- **Сервис** — гейтируемый порт-форвард: stage1/stage2/token порты + NAT на
  внутренний `host:port`. Пример: `ssh-home`.
- **Юзер** (в коде/конфиге исторически `client`) — личность с PSK, которой
  разрешён набор сервисов.
- **Токен** — НЕ объект настройки. Эфемерное значение, которое клиент
  пересчитывает каждые `bucket_seconds` из (psk, сервис, юзер, время). Управляем
  только роутерами/сервисами/юзерами.

## Модель данных: один конфиг, много роутеров

Сервисы и юзеры принадлежат конкретному роутеру. Целевая схема:

```yaml
routers:
  router-a:
    address: router.example.com
    defaults: { bucket_seconds: 30, ... }
    services: { ssh-home: {...}, web-home: {...} }
    clients:  { phone: {...}, laptop: {...} }
  home:
    address: 10.0.0.1
    services: {...}
    clients:  {...}
```

Следствия для реализации:

- `config` пакет: `Config` → `routers` map; `Load`/`Validate`/`Resolve`
  становятся router-scoped.
- **config-hash — per-router** (по срезу конкретного роутера). Deploy сравнивает
  hash среза с `mkpk-tt-meta` на этом роутере. Рендер идёт по срезу одного
  роутера (его сервисы+юзеры).
- `admin`-ядро: все операции получают параметр роутера; deploy — на выбранный
  роутер.

## Юзер × сервис (матрица доступа)

Юзер имеет **набор** сервисов. Имя сервиса входит в формулу токена
(`sha512(psk|v1|service|client_id|bucket|psk)`), поэтому при **одном PSK на
юзера** токены per-service всё равно разные — токен одного сервиса не открывает
другой.

- Единица рендера — пара **(юзер × сервис)**: свои token-правила и hit-списки на
  каждом сервисе, имена вроде `mkpk-tt-hit-now-<user>-<service>`.
- Это **не** «один knock открывает всё»: каждый сервис открывается своим
  отдельным knock на свои порты своим токеном.
- Runtime `mkpk knock` получает аргумент `--service`, чтобы выбрать, какой сервис
  открываем.
- `client.service: string` → `client.services: [string]`.
- Тоггл сервиса `enabled: bool`: выключенный сервис остаётся в конфиге, но его
  stage/token-правила, NAT и токены его юзеров не рендерятся/не деплоятся.

## Админский конфиг ≠ клиентский срез

Админский `mkpk.yaml` содержит PSK всех юзеров и SMTP-секреты — его юзеру
отдавать нельзя. Юзеру уходит **per-user срез**: адрес роутера, `bucket_seconds`,
только разрешённые ему сервисы (их порты + порт для TCP-check) и **его** один
`client_id`+`psk`.

## Раздача: per-user invite-blob

Основной способ доставки — компактная строка-инвайт (base64url от мини-JSON):

```json
{
  "router": "router.example.com",
  "bucket_seconds": 30,
  "user": { "client_id": "phone", "psk": "..." },
  "services": [
    { "name": "ssh-home", "stage1": 41011, "stage2": 41012, "token": 41013, "check_port": 2022 }
  ]
}
```

- Админ генерит блоб per-user (кнопка в UI / команда CLI), передаёт юзеру
  **только в safe-env** (не по открытым каналам).
- Клиентское приложение декодирует блоб → эквивалентный минимальный in-memory
  конфиг → переиспользует существующие `mkpk knock` / `mkpk check` (список
  портов, open/closed, стук). Новый код на клиенте минимален.
- Изменения (добавили сервис, ротация PSK) → админ пере-выдаёт новый блоб.
  Тихого авто-обновления нет — это осознанный компромисс.

### Почему не pull с роутера

Вариант «клиент знает только адрес+PSK и стучит за конфигом на роутер» отклонён:
чтобы вернуть конфиг, роутер должен ОТВЕЧАТЬ данными — это отвечающий сервис,
торчащий наружу (ломает stealth) и практически нереализуемый на ROS-only (та же
стена, что и с полноценным verifier). Единственный плюс pull — авто-рефреш —
не перевешивает. При реальной необходимости авто-обновления к нему можно
вернуться позже через отдельный лёгкий провижн-сервис в safe-сети (осознанный
отход от «ничего лишнего»), но это не первый шаг.

## Безопасность блоба

Блоб несёт всё состояние одного юзера (адрес, его PSK, его сервисы/порты). Его
компрометация = компрометация доступа этого юзера (не других — у каждого свой
блоб/PSK). Требование: передача блоба только в safe-env. См. threat-model.
